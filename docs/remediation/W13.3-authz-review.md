## Controls inspected

- Authorization is a transport-independent port in `internal/authz`.
- Policy evaluation is default-deny and emits stable, non-resource-revealing
  deny reasons.
- Tenant and workspace context is derived from the verified `domain.Principal`;
  request tenant values are never used as authority.
- Opaque resource resolution is keyed by `(tenant, kind, opaque-id)`.
- `Enforce` is the use-case seam and must run before repository access;
  `NewAuthorizedStore` accepts only an authorized context.
- Audit events contain correlation, actor, action, resource kind, decision and
  reason only; no token, content or secret is recorded.
- PostgreSQL RLS remains the database backstop (`migrations/v2/100_server.sql`).

## Gate verdict

## Remediation status

The W13.3 follow-up makes the conditional controls fail closed in server mode:

- The PostgreSQL composition root now creates an `AuthorizedContext` and uses
  `NewAuthorizedStore`; the raw `Store` is not placed in the runtime transport
  surface.
- Project access requires an explicit principal grant even for tenant admins,
  and the selected workspace must be present in the principal grants.
- The unsafe caller-selected `cortex_set_tenant(uuid)` function was removed.
  `cortex_bind_principal(uuid,text,bigint)` derives the tenant from an active,
  non-revoked actor row and atomically checks the grant digest and version. The application
  authentication layer is trusted to supply the actor public ID; it can no
  longer supply a tenant ID.
- Repository predicates retain explicit tenant/workspace checks in graph,
  scoring, bulk, and observation paths in addition to PostgreSQL RLS.

Docker negative integration, race/fuzz/mutation, coverage, vet, lint, and
zero-CGO gates remain release checks and must run with a real non-superuser
PostgreSQL DSN in CI.
